# Remove the CopyOnWrite dependency; rely on native OS block cloning

## Goal

Drop the `CopyOnWrite` NuGet dependency from this fork and rely on the block cloning that
Windows performs natively inside the `CopyFile` API suite.

## Background

Microsoft's own `CopyOnWrite` README states the library is superseded by CoW support built into
Windows 11 24H2 and Windows Server 2025, where CoW is automatic for Dev Drive and ReFS volumes.
Microsoft Learn confirms block cloning occurs natively in supported Windows copy operations from
those builds onward. A plain `File.Copy` on a Dev Drive therefore already clones; measured here
at 7.6 ms for a 2 GB file.

The library's manual FSCTL path is not merely redundant on such a machine, it is broken: on
Windows 25H2 with the .NET 11 preview SDK, `CloneFile` throws

    TypeLoadException: GenericArguments[0],
      'Microsoft.CopyOnWrite.Windows.NativeMethods+DUPLICATE_EXTENTS_DATA',
      on 'System.StubHelpers.IArrayMarshaler`2[T,TSelf]' violates the constraint of type parameter 'T'
      at NativeMethods.DeviceIoControl(...)

This surfaced only after the NuGet package root and the repository were moved onto the same ReFS
Dev Drive, which is the condition under which `_canCloneInNugetCachePath` first becomes true.
All servers in this environment target .NET 11.

## Scope

1. `Directory.Packages.props` — remove the `CopyOnWrite` `PackageVersion` (currently 0.5.0).
2. `src/Common/Microsoft.MSBuildCache.Common.csproj` — remove the `CopyOnWrite` `PackageReference`.
3. `src/Common/Caching/CacheClient.cs`
   - remove the `_copyOnWriteFilesystem` field and the `_canCloneInNugetCachePath` assignment,
   - remove the clone branch in `CopyPackageContentToDestinationAsync`, leaving the existing
     `File.Copy(..., overwrite: true)` as the single path,
   - remove the now-unused `using Microsoft.CopyOnWrite;`.
4. `src/Common/MSBuildCachePluginBase.cs` — remove the CoW support-warning block and its `using`.

Search for any remaining `CopyOnWrite` references before finishing; the scope above was derived
from a regex sweep and may be incomplete.

## Consequence, accepted deliberately

On Windows older than 24H2 this fork loses copy-on-write placement and falls back to real copies.
That is acceptable for this environment and is the reason the change belongs in the fork rather
than upstream. It also makes the fork permanently divergent from upstream on this point.

  package from the dotnet-public feed, so until then this fork is not what runs.

## Acceptance

- No `CopyOnWrite` reference remains in the repository.
- The solution builds.
- Package placement still succeeds, using `File.Copy`.
## Outcome

All four scoped files were changed and the solution builds clean. Three deviations worth recording.

**The method removal could not be done with the editing tools.** `str_replace` splits a C# file
into disjoint code, comment and literal regions and matches within one region only, so no pattern
— not even `[\s\S]*?` — can span `WarnOnCowWithDifferingVolumes`, whose body contains three string
literals. `run_solution_editor` refused the file outright because
`Microsoft.MSBuildCache.Common.csproj` multi-targets net472 and net9.0, giving two Roslyn
documents for one physical path and an ambiguous semantic edit target. The method was therefore
removed as text, from its signature to the first four-space closing brace (1143 characters).

If this file needs semantic edits again, scope the transaction to a single target framework, or
teach `run_solution_editor` to accept an explicit project/TFM when a path resolves to several
documents.

**IDE2000 is an error in this repository.** The deletion left two consecutive blank lines and the
build failed on that alone. Collapsed runs of three or more newlines back to two.

**This fork cannot be built through the CSharpEditor host.** `global.json` asks for SDK 10.0.100
with `rollForward: latestFeature`, and 10.0.400 is installed, so the ordinary CLI resolves it.
CSharpEditor builds through a private instrumented host at
`%LOCALAPPDATA%\CSharpMpc\toolchains\msbuild-reportfileaccesses\...\sdk` that carries only
11.0.100-preview.7, and `latestFeature` never rolls across a major version. Verification was done
with `dotnet build` from the worktree instead. `CSHARPMPC_SDK_DOTNET` exists to point that host
elsewhere if this needs to work.

**Incidental formatting churn.** `edit_xml` round-trips through `XDocument`, so
`Directory.Packages.props` also gained a space in the `NETStandard.Library` tag and lost one blank
line, and `Microsoft.MSBuildCache.Common.csproj` lost a trailing blank line. No semantic effect.

**Correction to the follow-up note.** Publishing "at a version above 0.1.328-preview" is not
required. CSharpMpc references an exact version, so ordering against Microsoft's package does not
matter; the local feed only has to carry the exact version referenced.
