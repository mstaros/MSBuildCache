# Record unchanged clean-list files as project outputs

A project's cache entry records only the files its build wrote. Incremental MSBuild skips copies and targets whose outputs are already current, so an entry recorded in a worktree where, for example, a referenced assembly's copy was already up to date lacks that copy. Another worktree that hits the entry keeps whatever older copy it holds. CSharpMpc's DependencyCopyCacheTests reproduces this, and a MerkleCompiler gate ran MpsAgent.ApiCatalog.Tests against a stale MpsAgent.ApiCatalog.dll this way.

- After the observed writes, read the project's clean list (`$(IntermediateOutputPath)$(CleanFile)`, MSBuild's FileListAbsolute.txt of files the build owns) and record each existing file under the repo root that is not ignored, not already recorded, and not another project's output.
- The ignored-output check moves to method scope so both loops share it.
- A new fingerprint entry describes the output rule, so entries recorded before this change are never reused.

## Summary

Cache entries now include the files a project's clean list owns even when an incremental build did not rewrite them, so a cache hit no longer leaves an older copy of a referenced assembly in place. Every cache key changes once.
Consumer impact: behavior - every project misses the cache once; entries include unchanged clean-list files
